# Architecture — Expense Tracker (Mobile)

**Status:** Phase 1 (MVP), Week 1 scaffold
**Owner:** Sonny (sonnyl@thecreditpros.com)

## 1. System overview

Offline-first mobile app. No backend, no network calls in Phase 1. All data lives in a local SQLite database on-device; receipt photos live on the device filesystem. The entire feature set must work in airplane mode.

```
┌─────────────────────────────────────────────┐
│                Expo Router (UI)              │
│   app/(tabs)/  Dashboard·Add·Expenses·        │
│                Reports·Settings               │
├─────────────────────────────────────────────┤
│         Zustand stores (store/)              │
│   useExpenseStore · useBudgetStore ·         │
│   useCategoryStore · useSettingsStore        │
├─────────────────────────────────────────────┤
│      Data layer (db/) — Drizzle ORM          │
│   schema.ts · queries/*.ts · migrations/     │
├─────────────────────────────────────────────┤
│   expo-sqlite (device DB) · filesystem       │
│        (receipt photos, CSV export)          │
└─────────────────────────────────────────────┘
```

Screens read/write through Zustand stores; stores call typed Drizzle query functions; nothing above the data layer touches SQL directly. This keeps a future sync layer (Phase 2) a data-layer-only change.

## 2. Architecture Decision Record (ADR)

### ADR-001: Mobile (React Native + Expo) over the org's web default

**Decision:** Build this as a React Native + Expo app, not React + Vite + Dexie.
**Context:** Sonny's `agent.md.md` sets React + Vite + Dexie/IndexedDB as the default for all builds. The product spec for this app explicitly calls for a native mobile app (App Store + Play Store distribution).
**Alternatives considered:** Web PWA (agent.md.md default) — faster to ship solo, no app-store review, but can't satisfy "native mobile app" distribution requirement, and IndexedDB can't back a relational reporting layer as cleanly as SQLite.
**Decision confirmed by Sonny on 2026-07-30.** This is a deliberate per-project deviation, not a change to the org default — `agent.md.md` is left as-is.

### ADR-002: Single-package repo, not a pnpm monorepo

**Decision:** One Expo app at the repo root; `types/`, `utils/`, `db/`, `store/` are plain root-level folders reachable via the `@/*` path alias, not workspace packages. (The Expo Router `tabs` template already establishes `@/*` → `./*` and root-level `components/`/`constants/` folders — the rest of the app code follows that same convention rather than introducing a separate `src/` root.)
**Context:** pnpm is not installed on the dev machine; Expo/Metro + pnpm workspaces still has open EAS Build detection bugs; there is exactly one consumer app.
**Consequence:** If a second app (e.g., a future web dashboard) needs to share types/utils, extract those folders into real packages then — a low-cost refactor. Reversing a broken monorepo mid-build would not be low-cost.

### ADR-003: expo-sqlite + Drizzle ORM over AsyncStorage or raw SQL

**Decision:** Local storage is SQLite via the `drizzle-orm/expo-sqlite` driver.
**Context:** Reports (category breakdown, monthly trend, budget-vs-actual) need relational queries (filter/group/aggregate) that AsyncStorage (key-value) cannot do. Drizzle adds compile-time query checking and generated migrations, which matter across 12 weeks of schema changes.
**Consequence:** Migrations are generated by `drizzle-kit` and must be bundled into the app (not read from disk at runtime) — wired once in Week 1 via `useMigrations`.

### ADR-004: Expo Router over bare React Navigation

**Decision:** File-based routing (`app/(tabs)/...`), which is built on top of React Navigation.
**Context:** Current default scaffold for new Expo apps; gives the 5-tab bottom nav the spec calls for with less boilerplate.

### ADR-005: react-native-gifted-charts over Victory Native / chart-kit

**Decision:** Use `react-native-gifted-charts` for the pie and trend-line charts.
**Context:** Covers both chart types in one library, SVG-based, works in Expo Go without a prebuild/dev-client. Victory Native XL requires `@shopify/react-native-skia` (native code, needs a dev build), which would slow down the Week 8-9 reporting work for no benefit at this scale.

### ADR-006: Local notifications only, no push

**Decision:** `expo-notifications` in fully local/device-scheduled mode.
**Context:** Zero-backend constraint. Push notifications require a server and platform credentials — out of scope until Phase 2 sync exists anyway.

### ADR-007: Detox E2E is Android-only for Phase 1

**Decision:** Accept that Detox iOS E2E cannot run on this Windows dev machine (no macOS = no iOS Simulator).
**Context:** Flagged now (Week 1) rather than discovered during Week 12 testing. iOS builds still ship via EAS cloud build; only _local E2E testing_ of iOS is blocked, not iOS distribution.
**Mitigation options for later:** cloud Mac CI runner, physical iOS device manual testing, or explicitly ship Phase 1 with Android E2E coverage only and note the gap in the release checklist.

## 3. Data flow: adding an expense (example)

1. User fills the Add Expense screen → local form validation (amount > 0, date not in the future unless recurring, category required).
2. Screen calls `useExpenseStore.addExpense(input)`.
3. Store calls `db/queries/expenses.ts#insertExpense`, a typed Drizzle insert.
4. If a receipt photo was attached, it's copied into the app's document directory with a generated filename and the path is stored on the row (see DATABASE_SCHEMA.md).
5. Store re-runs the relevant live queries (via Drizzle's `useLiveQuery`), so the Dashboard/Reports screens update reactively without manual refresh calls.
6. If the expense pushes a budget over its alert threshold, the store schedules a local notification (Week 10-11 work; stubbed in Week 1).

## 6. Known limitation: `npm run web` cannot query the database at runtime

The app **bundles** for web (`expo export --platform web` succeeds, see ADR-003's migration wiring) and now **opens** the database on web too (see ADR-008), but Drizzle's actual query execution (`db.select()`, `db.insert()`, etc.) still fails on web. This was investigated in three stages, each a distinct upstream issue, not an application bug:

1. **`SharedArrayBuffer is not defined`** — `expo-sqlite`'s web backend (`wa-sqlite`) needs `SharedArrayBuffer`, which browsers only expose on cross-origin-isolated pages. **Fixed**: `metro.config.js` now injects `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` via `server.enhanceMiddleware` (dev server only — a hosted/static web build would need the same two headers set by whatever serves it).
2. **`Sync operation timeout` on `openDatabaseSync`** — expo-sqlite's web implementation fakes synchronous DB opening with a Web Worker + `SharedArrayBuffer`/`Atomics` busy-wait (OPFS access is inherently async), and that busy-wait doesn't reliably resolve in time. **Fixed** by ADR-008: switched to `openDatabaseAsync`, which sidesteps this path entirely and is cross-platform-safe (native works the same or better).
3. **`Unterminated string in JSON` from `invokeWorkerSync` during `db.select()`** — Drizzle's `expo-sqlite` driver executes queries (not just the initial open) via expo-sqlite's synchronous statement methods (`getAllSync` etc.), which hit the _same_ Worker+Atomics mechanism from #2, and its result-serialization has a bug/limitation on web. **Not fixed.** A web search turned up other developers hitting adjacent failures (a "database is locked" error) in this exact Drizzle+expo-sqlite-web combination — this looks like a genuine, currently-unresolved gap between Drizzle's expo-sqlite driver and expo-sqlite's web backend, not something fixable from application code without forking a dependency.

**Current state: `npm run web` opens the database but cannot run queries.** Given web is Phase 2+ scope (mobile-first per the original spec) and this is an upstream library gap rather than our bug, it isn't being chased further right now — revisit when Drizzle/expo-sqlite ship a fix, or when Phase 2 actually prioritizes a web target. **Use Expo Go on a physical device to see the running UI** (see README.md) — native is unaffected by any of this, since native's synchronous SQLite calls are true JSI calls, not a Worker/Atomics emulation.

### ADR-008: `openDatabaseAsync` instead of `openDatabaseSync`

**Decision:** `db/client.ts` opens the database asynchronously (`initDb()`, awaited by `DatabaseProvider` before rendering children) instead of synchronously at module load.
**Context:** Needed to fix the web `Sync operation timeout` (see above). Kept even though full web querying still doesn't work, because it's a genuine improvement on native too — no blocking work at module-import time — with no behavioral downside.
